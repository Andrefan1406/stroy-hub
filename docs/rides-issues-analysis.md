## Проблема 1. Заявка «пропала» после переброски машины

### Жалоба пользователей

Диспетчер сделала «перебросить машину» и закрепила её за водителем. Заявка исчезла: нет в журнале, нет в пуле, у водителя тоже пропала. Базовая заявка «испарилась».

### Что происходит в коде

Переброска — эндпоинт `POST /:id/pull` (`server/rides/requestsRouter.js`, около строки 376). Он переводит заявку в состояние:

```
status = 'pending_assignment', driver_id = NULL, on_hold = 1, pull_reason = <причина>
```

Это состояние «снята с машины, ждёт решения заказчика». Оно скрыто из всех списков, кроме одного:

| Место | Почему там нет заявки |
|---|---|
| Пул водителей (`GET /pool`, ~стр. 192) | фильтр `on_hold = 0` |
| Журнал (`GET /history`, ~стр. 274) | только `completed` и `cancelled` |
| Список водителя (`GET /my-current`) | `driver_id` обнулён; водителю шлётся сокет-событие `request:pulled`, карточка убирается |
| **Вкладка «Текущие» у диспетчера** | **заявка видна** с плашкой «Снята с машины — ждёт решения заказчика» (`DispatcherRidesPage.jsx` ~408–410) |

Заявка не удаляется: она остаётся в «Текущих». Дальше её может вернуть в работу:
- заказчик через `POST /:id/hold-decision` (`requeue` — в пул, `cancel` — отменить);
- диспетчер кнопкой «Дать другую машину» (`POST /:id/assign` работает и для `on_hold`).

Отдельный статус для «снята с машины» не заводили: потребовалась бы пересборка таблицы из-за CHECK на `status` (см. комментарий в `server/rides/db.js`).

### Риски и слабые места

1. **Нет таймаута.** Если заказчик не ответил (не в сети, не получил уведомление `request:reassigned`), заявка висит в `on_hold` бессрочно: из пула скрыта, в журнале её нет.
2. **Потеря попутной заявки при сбое.** В `/pull` сначала фиксируется транзакция (у A снята машина), и только потом отдельным шагом вызывается `dissolveMergesForA` (`server/rides/mergeApply.js`), который возвращает влитые попутные заявки B в пул. Между шагами B остаётся в состоянии `status='assigned'`, `driver_id=<старый>`, `merged_into=A`:
   - у водителя её нет (`/my-current` фильтрует `merged_into IS NULL`);
   - в пуле её нет (не `pending_assignment`).
   Если процесс упадёт или `dissolveMergesForA` бросит исключение, B останется так навсегда. То же верно для `/unassign`, `/cancel` и `declineRequest` (`driverActions.js`).
3. **Слабая заметность** заявок `on_hold` у диспетчера: только счётчик и плашка внутри общего списка.

### Побочное наблюдение: объединённые заявки закрываются вместе

Из голосовых сообщений: две объединённые заявки (базовая, 3 серии и Козы Бигбусынова) закрываются одновременно. Это **заложенное поведение**: `cascadeCompleteMergedB` (`mergeApply.js`) вызывается при завершении A и переводит все попутные B в `completed` («одна поездка обслужила обе»). Баг ли это для пользователей — вопрос к заказчику.

### Предлагаемые правки

1. Выполнять `dissolveMergesForA` **внутри той же транзакции**, что и переброска/снятие/отмена/отказ. Рекомендуется.
2. Отдельный фильтр и счётчик заявок «снята с машины» у диспетчера; предупреждение, если уведомление заказчику не доставлено. Рекомендуется.
3. **Таймаут решения заказчика:** через N минут возвращать заявку в пул или напоминать диспетчеру. Значение N и действие нужно согласовать.

### Как проверить на конкретной заявке

```sql
SELECT * FROM request_events WHERE request_id = ? ORDER BY id;
-- ищем типы: reassigned, dispatcher_assigned, merge_dissolved, reassign_resolved

-- зависшие заявки:
SELECT id, status, driver_id, merged_into, on_hold, pull_reason FROM requests WHERE on_hold = 1;
SELECT b.id, b.merged_into, a.status AS a_status
  FROM requests b JOIN requests a ON a.id = b.merged_into
 WHERE b.merged_into IS NOT NULL AND a.status NOT IN ('assigned', 'in_progress');
```

Нужны номера пропавших заявок от пользователей, чтобы определить причину точно (сейчас это гипотеза по коду, не воспроизведённая).

## Проблема 2. Адреса других городов определяются как Усть-Каменогорск

### Жалоба

Сервис настроен на заявки по городу, но пользователи вводят адреса в других городах (Алтай, Шемонаиха). Заявки ошибочно получают улицы города Усть-Каменогорска.

### Причина

Геокодирование (`server/rides/routeEstimate.js`, функция `geocodeRaw`) идёт через Nominatim с `viewbox=82.20,49.70,83.05,50.20` и `bounded=1` (константа `GEOCODE_VIEWBOX`, можно переопределить переменной окружения `RIDES_GEOCODE_VIEWBOX`). Это прямоугольник около 60×55 км вокруг Усть-Каменогорска. Его добавили, чтобы «Крылова» не находилась в Алматы.

- Шемонаиха (~50.6°N, 81.9°E) и Алтай (бывший Зыряновск, ~49.7°N, 84.3°E) за пределами прямоугольника.
- `bounded=1` отбрасывает кандидатов вне прямоугольника. Название города в тексте адреса — не фильтр, а часть строки поиска.
- «г. Шемонаиха, ул. Ленина, 5» → находится «ул. Ленина, 5» в Усть-Каменогорске. Это дом, точность высокая, статус `found`, форма пишет «✓ найден».
- Отметить точку на карте требуется только для статусов `street`, `not_found`, `unavailable` (`server/rides/addressCheck.js`). Ошибочный адрес проходит как верный.

Итог: текст адреса верный (его видит водитель), а координаты, маршрут, время в пути и километраж посчитаны по Усть-Каменогорску.

### Усугубляющие факторы

1. **Кэш:** результат хранится в `geocode_cache` по тексту адреса 30 дней (`GEOCODE_TTL_DAYS`). Ошибочные координаты будут отдаваться, пока кэш не очистят (нужна миграция по образцу `server/rides/fixGeocodeRegionBug.js`).
2. **Карта по умолчанию:** `src/rides/MapPicker.jsx` стартует с центром Усть-Каменогорска.
3. **Нет сверки города:** ни сервер, ни форма не сравнивают город из адреса с городом найденной точки.

### Варианты исправления

1. **Расширить область поиска** до региона ВКО (примерно `80.0,48.5,87.5,51.5`). Алтай и Шемонаиха начнут находиться, Алматы останется исключён. Делается без кода через `RIDES_GEOCODE_VIEWBOX`. Рекомендуется.
2. **Сверять город:** если в адресе указан город, брать из ответа Nominatim результат с этим городом в `address`; иначе считать адрес ненайденным и требовать точку на карте. Защита от одинаковых названий улиц. Рекомендуется.
3. **Поле «Город» в форме** (по умолчанию Усть-Каменогорск), город добавляется в запрос. Самый надёжный вариант, но меняет форму. По желанию.
4. **Исправить прошлые заявки:** найти активные заявки, у которых в адресе чужой город, а координаты внутри Усть-Каменогорска; очистить кэш и пересчитать оценки. Рекомендуется.
