# Система служебного транспорта (заявки на поездки)

Аналог агрегатора такси для служебных легковых поездок компании. Сотрудник
подаёт заявку → она сразу попадает в общий пул → свободные водители видят
её одновременно и берут первым нажатием («Взять заказ») → диспетчер только
наблюдает и вмешивается вручную лишь как исключение (принудительное
назначение / отмена).

### Изменение маршрута уже поданной заявки (точки в пути)

Заказчик и водитель могут **предложить** добавить/изменить/убрать точку
маршрута (`stop_proposals`). Предложение висит `pending`, пока диспетчер
не одобрит или отклонит (`/api/v1/requests/stop-changes/...`). Диспетчер и
сам заказчик заявки, ещё не взятой из пула, применяют изменение сразу.
Провисевшие дольше `RIDE_PROPOSAL_TIMEOUT_MINUTES` предложения
авто-отклоняются джобой `proposalTimeout.js`. Одобренное предложение
правит `request_stops` (новая точка встаёт «по ближайшему участку»
маршрута), запускает `recomputeRequestEstimate` и рассылается сокетом
всем причастным. Всё логируется в `request_events` (см. вкладку «Журнал»
на `/rides-admin`).

### Объединение заявок водителем (П.6)

Водитель с активной заявкой A предлагает подвезти попутно заявку B из
пула: `POST /api/v1/requests/:bId/merge` c `{ intoRequestId: aId }`.
Нужно двойное согласие — заказчик A и диспетчер (`POST
/api/v1/requests/merges/:id/approve|reject`). Пока оба не «за» — B «мягко»
заблокирована в пуле (`merge_lock`, из пула пропадает). Оба «за» → точки B
вливаются в маршрут A (`request_stops.merged_from_request_id = B`),
`B.merged_into = A`, считается `pickup_eta_at`, идёт пересчёт маршрута.
Таблица `request_merges`. Таймаут 5 минут → `auto_rejected` (та же джоба
`proposalTimeout.js`). Завершение A каскадом закрывает влитые B; отмена /
отказ / переброска A — расформировывает объединение и возвращает B в пул
(`mergeApply.dissolveMergesForA`).

### Экстренная переброска машины (П.4)

`POST /api/v1/requests/:id/pull` (диспетчер) снимает машину с активной
заявки (`assigned`/`in_progress`): заявка получает `on_hold = 1` (в пул не
отдаётся), водитель освобождается либо сразу передаётся указанной
`targetRequestId`. Снятый заказчик получает сокет `request:reassigned` с
причиной и решает через `POST /:id/hold-decision` — `requeue` (вернуть в
общий пул) или `cancel`. Диспетчер вместо заказчика может дать другую
машину обычным `POST /:id/assign` (он теперь принимает и `on_hold`).

### Прогноз времени и занятость парка

`recomputeRequestEstimate` держит в `requests.expected_completion_at`
ориентировочный момент освобождения машины (учитывает число точек
маршрута; пересчитывается при добавлении точки и при выходе водителя в
рейс). `GET /api/v1/fleet-status` отдаёт агрегат: есть ли свободные машины
и, если нет, — минимальный `expected_completion_at` среди занятых. Форма
подачи заявки (`/employee`) показывает это баннером, диспетчер — карточкой
и колонкой «Освободится».

Роли в `rides.users`: `employee` (заказчик), `dispatcher`, `driver`.
Отдельной роли "админ поездок" нет — справочники водителей и машин
(CRUD) ведёт диспетчер, это та же роль, что и мониторинг заявок. Роли
всем назначает только главный админ сайта (`ADMIN_EMAIL` из
`server/adminAuth.js`, тот же, что и у общего `/admin`) — у него самого
в `rides.users` записи нет вообще: он не сотрудник/диспетчер/водитель, а
отдельная функция сверху, определяется по email, а не по роли. Он же
может только читать (не редактировать) справочники водителей/машин на
`/rides-admin`.

## Стек

- Backend: Node.js + Express, роутеры в `server/rides/`
- БД: SQLite (`better-sqlite3`), файл `server/rides/data/db.sqlite`
  (создаётся автоматически, в git не попадает — см. `.gitignore`)
- Реалтайм: Socket.io (комнаты `drivers`, `dispatcher`, `employee:{id}`, `driver:{id}`)
- Аутентификация: тот же Firebase Auth, что и у остального сайта — своего
  JWT/паролей нет. Валидного логина недостаточно для доступа: нужна ещё и
  запись в таблице `users` этого модуля с ролью (её создаёт admin на
  странице `/rides-admin`)

## Запуск

Из корня проекта (там же, где обычный `npm install`/`npm start` для
остального сайта):

```bash
npm install
```

Два процесса, в двух терминалах (как и весь остальной сайт — единого
`npm run dev` в проекте нет):

```bash
npm run server   # backend, включая /api/v1/* и Socket.io — http://localhost:4000
npm start        # frontend — http://localhost:3000
```

## Тестовые данные

```bash
npm run rides:seed
```

Добавит 2 водителей, 2 машины, 2 сотрудника, диспетчера и 2 тестовые
заявки в пуле. **Важно:** email в сиде — вымышленные. Чтобы
реально войти под одним из них, под тем же email должен существовать
аккаунт в Firebase Authentication проекта — сид этого не делает, он только
заполняет SQLite.

Завести сами аккаунты в Firebase Authentication (email/пароль из
`create-test-users.js`, совпадают с email из сида) можно одной командой —
нужен service account ключ именно проекта `my-first-site-16a0c`
(Firebase Console → Project Settings → Service accounts → Generate new
private key; НЕ коммитить в git):

```bash
GOOGLE_APPLICATION_CREDENTIALS=./путь/к/ключу.json npm run rides:create-test-users
```

### Тот же ключ нужен для работы `/rides-admin` (и локально, и на Render)

Вкладка «Роли» вызывает `GET /api/v1/users`, а он читает список
пользователей Firebase через `listUsers()` — эта операция, в отличие от
проверки токена при логине (`verifyIdToken`, ей хватает одного
`projectId`, см. `server/adminAuth.js`), требует полноценных credentials.
Без них сама страница `/rides-admin` открывается, но эта вкладка
отвечает «Не удалось получить список пользователей Firebase».

Для самого backend-процесса (не для разового скрипта выше) ключ задаётся
**не** через `GOOGLE_APPLICATION_CREDENTIALS` (это путь к файлу на диске —
на Render такого файла нет), а тем же способом, что уже используется в
проекте для Google Sheets (`GOOGLE_SHEETS_SERVICE_ACCOUNT_JSON`, см.
`server/googleSheetsClient.js`) — весь JSON-ключ одной строкой в
переменной окружения:

```
FIREBASE_SERVICE_ACCOUNT_JSON={"type":"service_account","project_id":"my-first-site-16a0c",...}
```

- **Локально** — строка в `.env` (gitignored).
- **На Render** — Dashboard сервиса → Environment → добавить переменную
  `FIREBASE_SERVICE_ACCOUNT_JSON` с тем же значением, затем передеплой.

Без этой переменной `server/adminAuth.js` по-прежнему инициализирует
Firebase Admin только с `projectId` — вход и проверка ролей везде на
сайте продолжают работать как обычно, не работает только `listUsers()`
на вкладке «Роли».

## Первый запуск: доступ к `/rides-admin`

Ничего заводить в БД не нужно — доступ главного админа к `/rides-admin`
(вкладка «Пользователи и роли» + просмотр справочников) определяется по
`ADMIN_EMAIL` в `server/adminAuth.js` напрямую, без записи в
`rides.users`. Если `ADMIN_EMAIL` уже правильный (`admin@vkdev.kz`) —
просто зайдите на сайт под этим email и откройте `/rides-admin`.

Дальше на вкладке «Пользователи и роли» назначьте роль `dispatcher` тому,
кто будет вести справочники водителей/машин и мониторить заявки — эта же
роль открывает ему полный (не только для чтения) доступ к вкладкам
«Водители»/«Машины» на `/rides-admin` и панель мониторинга на `/dispatcher`.

## Настройки

- `RIDE_STALE_THRESHOLD_MINUTES` — за сколько минут до времени подачи
  заявка без водителя подсвечивается диспетчеру (по умолчанию 15; после
  наступления времени подачи — тоже подсвечена).
- `RIDE_DRIVER_BUFFER_MINUTES` — запас между заказами одного водителя на
  дорогу до следующей подачи (по умолчанию 15): после поездки 17:00–18:00
  следующая подача — со слота 18:15. См. `driverAvailability.js`.
- `RIDE_DEFAULT_TRIP_MINUTES` — сколько длится поездка для расчёта
  занятости водителя, если маршрут не удалось построить (по умолчанию 30).
- `RIDE_PROPOSAL_TIMEOUT_MINUTES` — сколько минут предложение по маршруту
  (добавить/изменить/убрать точку) ждёт решения диспетчера, прежде чем
  джоба `proposalTimeout.js` авто-отклонит его (по умолчанию 5).
- `RIDES_DATA_DIR` — путь к SQLite-файлу, если нужно переопределить (на
  хостинге без примонтированного диска БД стирается при каждом деплое —
  тот же приём, что и у `CONCRETE_DATA_DIR` в остальном проекте).
- `RIDES_GEOCODE_VIEWBOX` / `RIDES_GEOCODE_COUNTRY_CODES` — геокодер
  (Nominatim) ищет адреса только в этом регионе (по умолчанию — окрестности
  Усть-Каменогорска, `kz`). Без этого одинаковые названия улиц в разных
  городах Казахстана (например, «Крылова» — и в Усть-Каменогорске, и в
  Алматы) иногда резолвились не в тот город, и маршрут "разъезжался" на
  сотни-тысячи км (см. `server/rides/fixGeocodeRegionBug.js` — одноразовая
  чистка старого кэша и пересчёт активных заявок после этого фикса).
  Переносите компанию в другой город — обновите оба значения.

## Telegram-бот для водителей

Код — `server/rides/telegram/`. Бот только для водителей: новые заявки
приходят водителям **на линии** (свободен/занят) карточкой с кнопкой
«Взять»; телефон и имя заказчика — только в карточке уже взятого заказа.
Меню: «Пул заявок», «Мои заказы» («Выехал», «Завершить», «Отказаться» с
причиной), «Выйти на линию / Уйти с линии». Все действия идут через
`driverActions.js` — тот же код, что у сайта, поэтому взятие в боте и на
сайте подчиняется одним правилам (первый успевший, занятость по времени).
Рассылка подписана на внутреннюю шину `ridesBus` в `socket.js` — те же
события, что получают страницы водителей.

Привязка: в кабинете водителя кнопка «Подключить Telegram» выдаёт
одноразовую ссылку `t.me/<бот>?start=<токен>` (15 мин). `/stop` в боте или
«Отключить» на сайте отвязывают; уволенный водитель отвязывается сам.
Диспетчер видит колонку «Telegram» в списке водителей на `/rides-admin`.

Настройка:
1. В @BotFather: `/newbot` → имя и username бота → токен. Владелец бота —
   лучше корпоративный аккаунт: токен привязан к нему.
2. Переменные окружения сервера (без `TELEGRAM_BOT_TOKEN` бот выключен):
   - `TELEGRAM_BOT_TOKEN` — токен из BotFather;
   - `TELEGRAM_WEBHOOK_SECRET` — любая длинная случайная строка;
   - `PUBLIC_BASE_URL` — внешний адрес сервера, например `https://xxx.onrender.com`.
   Сервер при старте сам регистрирует webhook `POST /api/telegram/webhook`
   и список команд. Сервер должен работать в одном экземпляре.
3. Локальная проверка — отдельный тестовый бот (один токен нельзя
   одновременно держать на webhook и на локальном опросе):
   `TELEGRAM_BOT_TOKEN=<тестовый>` и `TELEGRAM_MODE=polling` — сервер сам
   опрашивает Telegram, внешний адрес не нужен.

Тесты: `npm run test:server` (`server/rides/tests/telegramBot.test.js`,
Telegram подменён поддельным API).
