# Модуль ПТО — ведомости по проектной документации

Этап 1: раздел **КЖ** (конструкции железобетонные).
Цепочка: **PDF раздела → ведомость материалов → виды работ → расценки → стоимость → Excel**.

Доступ — только `admin@vkdev.kz` (`access.js`: один список email; зеркало для фронтенда —
`src/pto/access.js`). Каждый `/api/pto/*` проверяет Firebase ID-токен и отвечает 403 остальным.
Интерфейс: `/pto` (карточка «ПТО» в личном кабинете `/admin`), код — `src/pages/PtoPage.jsx`, `src/pto/`.

## Файлы

| Файл | Что делает |
|---|---|
| `db.js` | отдельный SQLite (`PTO_DATA_DIR`): документы, строки ведомости, работы, запомненные расценки, цены на материалы |
| `pdf.js` | текст с координатами из векторного PDF (pdfjs-dist); скан без текстового слоя — понятная ошибка |
| `parsers/steelSummary.js` | сводная «Ведомость расхода стали, кг» (по элементам, классам, диаметрам, закладные) |
| `parsers/specification.js` | «Спецификация …» элемента: бетон, арматура по группам, прочий металл; число элементов |
| `parsers/kzh.js` | раздел КЖ целиком; сбой листа попадает в отчёт и не останавливает остальные |
| `consolidate.js` | объединение одинаковых позиций с разных листов (листы-источники сохраняются) |
| `works.js` | виды работ из материалов (армирование, закладные, бетонирование, бетонная подготовка) |
| `reconcile.js` | сверка спецификаций со сводной ведомостью стали, предложение коэффициента |
| `rates.js` | подбор расценок по своду (Qdrant) + арбитр-модель |
| `service.js` | вся логика поверх БД; `router.js` — HTTP; `excel.js` — выгрузка |
| `sections.js` | реестр разделов: чтобы добавить АР/КР/ОВ/ВК/ЭОМ — свой разбор и правила работ здесь |
| `tools/parse-file.js` | разбор файла без сервера: `node server/pto/tools/parse-file.js "<pdf>" --rows` |

## Как считается

* **Сводная ведомость стали** — основной источник по арматуре и закладным (`basis = summary`, в расчёте).
  Арматура по спецификациям (`basis = spec`) в расчёт не входит, пока есть сводная (серые строки), — это для сверки.
  Бетон берётся только из спецификаций. Прочий металл (труба, лист, МН) — справочно: на него нет цены.
* **Спецификация даётся на один элемент.** Если в таблице есть строка-название с числом элементов
  («Плита ППдм 1 — 2»), расход умножается на него (проверено: плиты сходятся со сводной ведомостью до 0,1 %).
  Для стен числа нет в самой спецификации — **сверка** показывает расхождение со сводной ведомостью
  (на примере: ×2,02 — две секции здания) и предлагает коэффициент; применяет его пользователь кнопкой.
* **Расценки:** сначала «утверждённые в VK», затем «ЕНиР для фирм» (для бригад — нет), **цена с НДС**.
  Предлагает ближайшая по смыслу из свода, арбитр (модель проекта) отсеивает смежное; без модели — только
  совпадения с близостью ≥ 0,65. Подтверждённое соответствие запоминается (`pto_price_mappings`) и применяется в
  следующих документах.
* **Материалы** — ориентировочные цены из `pto_material_prices` (арматура 400 000 ₸/тн, бетон 40 000 ₸/м³),
  меняются на вкладке «Итого». Утверждённого прайса пока нет.
* Всё извлечённое — «черновик» до проверки; ручные правки помечаются («✎ изменено», «＋ вручную»).

## Эксплуатация

* Загрузка — сырое тело `application/pdf` (до `PTO_MAX_UPLOAD_MB`, по умолчанию 100), разбор в фоне,
  документ в статусе «parsing», пока не готовы и ведомость, и расценки. Сам файл **не сохраняется**.
* На 41 МБ / 118 листов: ~13 с на разбор, ~350 МБ RSS процесса. На хостинге с 512 МБ памяти запас небольшой.
* Данные лежат в `PTO_DATA_DIR` (по умолчанию `server/pto/data/`, в `.gitignore`); на хостинге с эфемерным
  диском нужен персистентный путь, иначе всё стирается при деплое.
* Тесты: `npm run test:pto` (доступ, весь HTTP-цикл, расценки, парсеры, чтение PDF). Тест на реальном КЖ
  запускается, если файл есть на машине (`PTO_SAMPLE_PDF` или `C:\Users\a.kuznecov\pto-samples\…`).
